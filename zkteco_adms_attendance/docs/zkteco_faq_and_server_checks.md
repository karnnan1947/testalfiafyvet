# ZKTeco ADMS Attendance — FAQ & Server-Side Checks

A plain-language Q&A covering how the ADMS push integration works, the auth token,
security (nginx / IP allow-list / VPN), **and how to verify a device from the Odoo
server using the command line.**

---

# Part A — How it works (Q&A)

### Q1. Does Odoo connect to the device, or the device to Odoo?
**The device connects to Odoo.** The ZKTeco terminal is the HTTP *client*; Odoo is only a
server that answers. Odoo never dials the device. So on the terminal you always enter
**Odoo's** address — never the device's own IP.

```
  DEVICE (caller)  ── "GET /iclock/cdata?SN=..." ──►  ODOO (answers)
                   ◄── "GET OPTION FROM: <SN> ..." ──
```

### Q2. How does Odoo know a device is Online?
Every time the device calls any `/iclock/...` endpoint, the controller runs
`device.mark_online()`, which stamps **Last Seen = now** and sets status to **Online**.
So **Online = "the device phoned in recently."** A healthy device heartbeats about every
30 seconds, so it stays green. *You click nothing — it is automatic.*

### Q3. How does Odoo know a device is Offline?
A background job (**cron, every 5 minutes**) checks each Online device: if **Last Seen** is
older than the company's "offline after N minutes" setting (default **5 min**), it flips the
device to **Offline** and raises a manager activity. Odoo cannot be *told* the device died
(the device is a client) — it only notices the silence.

| Status | Meaning |
|--------|---------|
| Draft | Registered, not activated — pushes rejected |
| Confirmed | Activated, waiting for first contact |
| 🟢 Online | Heard from it within the last few minutes |
| 🔴 Offline | Silent for 5+ minutes |

### Q4. Which button do I click to connect it? Is it automatic?
Only **one** button: **Confirm** (Draft → Confirmed). After that it is 100% automatic —
when the device calls in, it turns Online by itself. There is **no "Connect" or "Go Online"
button.**

### Q5. What is the Auth Token and where does it come from?
It is a random secret **generated by Odoo** (not by ZKTeco). It is created in exactly one
place — when you click **Confirm** (`auth_token = uuid.uuid4().hex`), e.g.
`a3f8c2e14b7d49a08f1e6c5b2d9a0e77`. The **Push Settings** button does *not* create it (that
button only queues INFO/OPTION commands for the device).

### Q6. Do I give the token to the customer to type into the device?
**No.** A SpeedFace-V5L has **no field** to enter a token; standard ADMS authenticates by
**Serial Number only**. Give the customer only: **Serial Number + Server Address + Port.**
For a normal setup, **leave the Auth Token empty** in Odoo → the device is accepted by its
serial number.

### Q7. Then why does the token feature exist?
To stop **forged punches**. A serial number is not secret, so anyone who reaches the endpoint
and knows the SN could POST fake attendance. A token would block them (they don't know the
secret). But since the real device also can't send the token, the token is only usable via a
**reverse proxy** that adds it — see Q8.

### Q8. Where is the token actually used? (reverse proxy)
Only server-side, by an nginx/proxy placed in front of Odoo that injects the secret:

```nginx
location /iclock/ {
    proxy_set_header X-ZKTeco-Token "a3f8c2e14b7d49a08f1e6c5b2d9a0e77";
    proxy_pass http://127.0.0.1:8069;
}
```
```
  DEVICE ──(SN only)──► NGINX ──(SN + secret header)──► ODOO ✅
```
The token lives in the proxy config; the device and customer never see it.

### Q9. But an attacker could send a fake SN to nginx and nginx adds the token anyway!
**Correct — the token alone does NOT stop that.** If nginx blindly adds the secret to
everything, a spoofer who reaches nginx gets it added for free. The token only blocks
attackers who **bypass nginx and hit Odoo directly**. The **real** defense against a spoofed
device is network-level (Q10), not the token.

### Q10. What actually protects against a spoofed device?
**Controlling who can reach the endpoint** — because ADMS has no real device identity, you
trust the *network path*, not the message.

```
  Layer 1  NETWORK    → keep /iclock/ on a private LAN/VPN, NOT the public internet   (main guard)
  Layer 2  IP ALLOW-LIST (nginx/firewall) → only the device's IP may hit /iclock/     (main guard)
  Layer 3  HTTPS      → so traffic can't be sniffed/replayed
  Layer 4  TOKEN      → last-ditch: blocks anyone slipping past nginx straight to Odoo (weakest)
```
Example nginx allow-list:
```nginx
location /iclock/ {
    allow 10.16.10.230;   # only the real device
    deny  all;            # everyone else → 403
    proxy_pass http://127.0.0.1:8069;
}
```

### Q11. We use a VPN / everything shares one IP — does IP allow-list still work?
It depends how the VPN assigns addresses:
- **Plain LAN (no VPN):** each device keeps its own IP (e.g. `10.16.10.230`) → allow-list
  works. **Simplest and recommended.**
- **Client VPN (per-device tunnel IP):** the device gets its own VPN IP (e.g. `10.8.0.5`) and
  needs VPN credentials to enter. The **VPN key** is the real guard; you can still allow-list
  the tunnel IP.
- **Site VPN / NAT (all share one exit IP):** IP allow-listing can only narrow trust to
  "inside the company." A malicious **insider** on that network is a residual risk. Mitigate by
  putting the device on its **own subnet/VLAN**; full fix (mTLS) isn't supported by ZKTeco.

**Honest bottom line:** ADMS cannot cryptographically prove "this is the real device." The
realistic threat is *outsiders on the internet*, and keeping the endpoint on a private
network stops them completely. A trusted-insider forging attendance is an accepted, low
priority risk for this kind of data.

### Q12. Recommended setup for a normal install
Device and Odoo on the same **private LAN**, endpoint **not exposed to the internet**,
**Auth Token empty**, device authenticated by **Serial Number**. If you must expose it,
put nginx in front with **HTTPS + `allow <device-ip>; deny all;`**.

# Part B — How to check a device from the Odoo **server** (command line)

> ⚙️ **Your hosting is Odoo.sh** — instance `jadeela-jadeela-staging-34618415`
> (Odoo 19, Ubuntu 24.04). **Use B0 below** — it uses the Odoo.sh shell commands from your
> Shell tab. The generic Linux/Windows commands in B1–B6 are only for a **self-hosted** server.

## B0. Checking on Odoo.sh (use this for your instance)

On Odoo.sh the device connects over the **public internet via HTTPS**, so in the device you
enter your **Odoo.sh domain** — *not* a LAN IP:

| Device (SpeedFace) setting | Value on Odoo.sh |
|----------------------------|------------------|
| Enable Domain Name | **ON** |
| Server Address | your Odoo.sh domain — the address you see in the browser when you open this staging DB (e.g. `…dev.odoo.com`, or your custom/production domain) |
| Server Port | **443** |
| HTTPS | **ON** |
| DNS (under `Menu ▸ COMM ▸ Ethernet`) | **required** — the device needs internet + name resolution |

**Odoo.sh shell commands (the Shell tab from your screenshot):**

**1) Did the device reach the server? — read the log (the #1 check):**
```bash
lnav ~/logs/odoo.log          # opens the log viewer; then type  /iclock  and Enter to search
# or a quick grep:
grep iclock ~/logs/odoo.log | tail -n 20
# live tail:
tail -f ~/logs/odoo.log | grep --line-buffered iclock
```
Look for `GET /iclock/cdata?SN=AJE1261000840 ... 200`:
- **present** → the URL is entered correctly in the device and it is reaching Odoo ✅
- **absent** → device is NOT reaching Odoo: wrong Server Address/Port, HTTPS off, or no DNS/internet on the device
- **401 / ACCESS DENIED** → it reached Odoo, but the SN isn't Confirmed or an Auth Token is set (clear it)

**2) What status does Odoo hold? — database shell:**
```bash
psql
```
```sql
SELECT device_name, serial_number, state, last_seen
FROM zkteco_biometric_device ORDER BY last_seen DESC NULLS LAST;
-- type \q to quit
```

**3) Same, via the Odoo shell:**
```bash
odoo-bin shell
```
```python
for d in env['zkteco.biometric.device'].search([]):
    print(d.serial_number, d.state, d.last_seen, '| logs:', d.log_count)
```

**4) Test the exact URL the device uses (proves the endpoint answers):**
```bash
curl "https://YOUR-ODOO.SH-DOMAIN/iclock/cdata?SN=AJE1261000840"
```
Expect `GET OPTION FROM: AJE1261000840 ...` — that is exactly what the device receives when the
URL is entered correctly.

**Not usable on Odoo.sh:** `tcpdump`, `netstat` device-filtering, `ping` the device, or editing
nginx / IP allow-lists — Odoo.sh is a managed sandbox and the device connects over the public
internet, not your LAN.

> 🔐 **Security note for Odoo.sh:** the `/iclock/` endpoint is **public**, and on Odoo.sh you
> cannot add an nginx IP allow-list or a token-injecting proxy. So anyone who knows the serial
> number could POST forged punches — the residual risk is *fake attendance*. If that matters,
> run the integration behind your **own reverse proxy / firewall** (self-hosted, or a proxy in
> front of a custom domain) instead of directly on Odoo.sh. On a private-LAN self-hosted setup
> this isn't an issue (the endpoint simply isn't reachable from outside).

### Self-hosted server reference (B1–B6)

*Only if you run Odoo on your own Linux/Windows server (not Odoo.sh).*
Replace `<DB>` with your database name, `AJE1261000840` with your serial, `10.16.10.230`
with the device IP, and `8069` with your Odoo/nginx port.

## B1. Is the device actually reaching Odoo? — watch the web log
Odoo logs every HTTP request. Each device contact appears with the device's **source IP** and
the `/iclock/cdata` path. This is the single most useful check.

**Linux (log file):**
```bash
# live view of device traffic
tail -f /var/log/odoo/odoo.log | grep --line-buffered iclock
# recent contacts only
grep iclock /var/log/odoo/odoo.log | tail -n 20
```
**Windows (Odoo started from a console):** watch the console window, or if you log to a file:
```powershell
Get-Content C:\path\to\odoo.log -Tail 20 -Wait | Select-String iclock
```
A healthy device produces lines like this every ~30 s:
```
10.16.10.230 - - [08/Jul/2026 09:00:01] "GET /iclock/cdata?SN=AJE1261000840&... HTTP/1.1" 200 -
```
- Seeing the **device IP + `/iclock/cdata` + `200`** repeatedly → **it is connected.** ✅
- Seeing **`401`** or `ACCESS DENIED` warnings → SN not Confirmed, wrong SN, or Auth Token set.
- Seeing **nothing** → the device isn't reaching Odoo (network / wrong server address / port).

## B2. What does Odoo think the status is? — query the database
```bash
# Linux
psql -U odoo -h localhost -d <DB> -c \
"SELECT device_name, serial_number, state, last_seen \
 FROM zkteco_biometric_device ORDER BY last_seen DESC NULLS LAST;"
```
```powershell
# Windows
& "C:\Program Files\PostgreSQL\16\bin\psql.exe" -U odoo -d <DB> -c "SELECT device_name, serial_number, state, last_seen FROM zkteco_biometric_device ORDER BY last_seen DESC NULLS LAST;"
```
- `state = online` and `last_seen` within the last few minutes → connected.
- `last_seen` old / `state = offline` → it stopped calling in.

## B3. Is attendance data actually flowing? — count raw punches
```bash
psql -U odoo -h localhost -d <DB> -c \
"SELECT d.serial_number, count(l.id) AS punches, max(l.punch_datetime) AS latest_punch \
 FROM zkteco_biometric_device d \
 LEFT JOIN zkteco_biometric_attendance_log l ON l.device_id = d.id \
 GROUP BY d.serial_number;"
```
A growing `punches` count and a recent `latest_punch` = data is arriving.

## B4. Same checks via the Odoo shell (no SQL)
```bash
python odoo-bin shell -c odoo.conf -d <DB>
```
```python
for d in env['zkteco.biometric.device'].search([]):
    print(d.serial_number, d.state, d.last_seen, '| logs:', d.log_count)
```

## B5. Test the endpoint yourself from the server
```bash
curl "http://localhost:8069/iclock/cdata?SN=AJE1261000840"
```
- Returns `GET OPTION FROM: AJE1261000840 ...` → Odoo + registration + token are all correct.
- Returns `ACCESS DENIED` → SN not Confirmed / wrong SN / Auth Token is set (clear it).
- Connection refused / timeout → wrong port or Odoo not running there.
> Note: running this marks the device Online (something just "called in" with its SN).

## B6. Network-level checks from the server
```bash
# Can the server even reach the device's network? (device must be reachable)
ping 10.16.10.230

# Who is currently connected to the Odoo port? (look for the device IP)
# Linux:
ss -tn | grep ':8069'
netstat -tn | grep ':8069'
# Windows:
netstat -ano | findstr :8069

# Live packet capture of device traffic (Linux, very powerful):
sudo tcpdump -nn -i any host 10.16.10.230 and port 8069
```
> ADMS calls are short, so `netstat`/`ss` may not catch a live connection at every instant —
> the **log watch (B1)** and **tcpdump** are the most reliable "is it talking right now" tools.

# Part C — 30-second "is my device connected?" checklist

1. **Odoo UI:** device status is 🟢 **Online** and **Last Seen** is recent. *(easiest)*
2. **Server log (B1):** `grep iclock` shows the device IP hitting `/iclock/cdata … 200` every ~30 s.
3. **Database (B2):** `last_seen` within a few minutes, `state = online`.
4. **Data (B3):** raw-log `punches` count increases after a test punch.

If all four agree → the device is genuinely connected and pushing. If the UI says Online but
no new punches arrive, the device only sends on real punches — do a test face/finger scan.

# Part D — Visual diagrams (reference)

### D1. Who calls whom (the core idea)
```
   DEVICE (the caller)                          ODOO (the server, only answers)
   e.g. 10.16.10.230                            your Odoo / Odoo.sh
        │                                              │
        │  ①  GET /iclock/cdata?SN=AJE1261000840       │
        │  ─────────────── request ──────────────────► │  ← request LANDS here (Odoo receives)
        │                                              │
        │  ②  "GET OPTION FROM: AJE1261000840 ..."     │
        │  ◄────────────── response ─────────────────  │  ← Odoo replies
```
Odoo never dials the device. You always enter **Odoo's** address in the device.

### D2. Online / Offline detection
```
   Device ── heartbeat every ~30s ──►  Odoo   : stamps "Last Seen = now", stays 🟢 Online
   Device goes silent (power/network) ─►  (nothing arrives)
   Odoo cron (every 5 min): Last Seen older than 5 min?  → 🔴 Offline + notify a manager
```
🟢 Online = "heard from it recently."  🔴 Offline = "silent for 5+ minutes."
You click nothing — both are automatic. The only button you press is **Confirm** (once).

### D3. The Auth Token — three situations
```
 (a) token EMPTY  (normal, recommended):
     Device ── SN ──►  Odoo                    → accept by Serial Number            ✅

 (b) token SET, no proxy  (why a plain device breaks):
     Device ── SN, no secret ──►  Odoo         → secret required, none sent → DENIED ❌

 (c) token SET, with a reverse proxy  (the only way it helps):
     Device ── SN ──►  nginx (adds X-ZKTeco-Token) ── SN + secret ──►  Odoo         ✅
```
The token is created by **Odoo on Confirm**, lives in the **proxy** config, and is **never**
typed into the device.

### D4. The spoofing gap and the real fix
```
 Problem — attacker reaches nginx, which blindly adds the token:
     Attacker ── fake SN ──►  nginx (adds token) ──►  Odoo   → accepted   ❌ BAD

 Fix — IP allow-list at nginx (network trust, not the token):
     Real device 10.16.10.230 ──►  nginx: allow  ✅ ──►  Odoo             ✅
     Attacker    203.0.113.9   ──►  nginx: deny all  ✗  →  403 (blocked before Odoo)
```

### D5. VPN / shared-IP cases
```
 Case A — Plain LAN (recommended): each device keeps a unique IP
     Device 10.16.10.230 ──►  Odoo            allow 10.16.10.230; deny all;   ✅

 Case B — Client VPN: device gets its own tunnel IP + needs a VPN key to enter
     Device ──(VPN key)──►  10.8.0.5 ──►  Odoo      allow 10.8.0.5; deny all; ✅

 Case C — Site VPN / NAT: everything shares ONE exit IP
     Device  ─┐
     Laptop  ─┤─►  gateway (one IP 203.0.113.7) ─►  Odoo   can't tell them apart ✗
     Insider ─┘                                            → put the device on its own VLAN
```

### D6. Security layers (strongest → weakest)
```
 Layer 1  NETWORK        keep /iclock/ on a private LAN/VPN, not public      ← strongest
 Layer 2  IP ALLOW-LIST  only the device's IP may hit /iclock/               ← strong
 Layer 3  HTTPS          traffic can't be sniffed / replayed
 Layer 4  TOKEN          blocks only those who bypass nginx straight to Odoo ← weakest
```
> On **Odoo.sh**, Layers 1 & 2 aren't available (endpoint is public, nginx is managed);
> Layer 3 (HTTPS) is automatic. That's why the Odoo.sh security note in Part B0 matters.
